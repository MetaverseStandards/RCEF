# Governance and release gates

Original documentation: CC-BY-SA-4.0.

Ken Jakubzak and the Forum's 3D Assets working group own repository publication and releases. The project decides who maintains it and who reviews meaning. This document does not claim a standards mandate or any outside approval.

A proposal states the problem, the public evidence, the effect on compatibility, the alternatives, the tests and the open questions. A signal ID stays the same when its label changes. A retired ID needs a documented tombstone. Schema, operator and data versions change independently. A change to meaning or licences needs review before it is published.

A vocabulary profile, such as the draft [canonical expression set](docs/canonical-set.md), has a `vocabulary_version` and a `vocabulary_status` in its metadata. Version 1.x may only add signals, and each addition raises the minor version. A change of meaning needs a new ID. Until a vocabulary is first accepted or released, edits to membership and definitions that keep every provider value are made in place, and its IDs may be renamed or withdrawn without a tombstone. After the meaning review, acceptance changes only `vocabulary_status`, from `draft` to `accepted`. It never changes IDs, calibration strings or maps. `accepted` is RCEF's own status. It is not a standard, an outside approval or an endorsement.

A data release needs complete selected inventories, a disposition for every signal, valid evidence references, deterministic packs, checksums and passing consumer tests. Unresolved evidence can be released as inventory if it is clearly labelled, but the executable mappings that depend on it stay unavailable. A release states the shared tooling commit it was tested with and the Python versions it actually ran on.

Review runtime behaviour separately from the taxonomy. Device support, rig deformation, VRM composition, Roblox certification and standards adoption each need their own measured acceptance. An exact scalar mapping certifies only its declared operation, within its assumptions.

Before you publish a release, check source provenance, inherited notices, generated bytes, the dependency pin, tests, documentation links and history. RCEF is a public repository in the Metaverse Standards Forum organization on GitHub: https://github.com/MetaverseStandards/RCEF.
